## Context

The owner, on 2026-11-19: «Otağın QR və kodunun yanında linki WhatsApp-a göndərmək olsun; linki açan «Qoşul» düyməsinə basmadan birbaşa otağa düşsün; hələ hesabı olmayan adam da linkdən çox rahat girə bilsin.»

What there is (ADR 020 decisions 3–4, ADR 026 decisions 6, 15–16, architecture §12 "Rooms and joining" and "Games first"):

- **The link.** `RoomJoinLink::of()` gives a room page `join`: `url`, `{APP_URL}/oyun/{code}` — the QR's address — and `entry_url`, `{APP_URL}/oyun`, the address said under it. The host's start screen draws the QR, the code and that line (`InviteCard`); a round's code chip and a player's «Dostunu çağır» open them in a dialog (`CodeDialog`); the big screen draws them as a poster. Nothing sends the link: people pass the code by voice, by showing the QR, or by typing the address into a chat by hand.
- **Opening it.** Every room route is in the player group (`rooms.enabled`, `auth`, `role.chosen`, `verified`, `role:player`). `GET /oyun/{code}` (`RoomJoinController::show`) shows `rooms/join` — the code, «Oyunda adınız belə görünəcək:», the account's name with «Dəyiş» into Settings → Profil, and «Qoşul» — or sends a present player to the room; `POST /oyun/{code}` is `JoinRoom`. Both count against `room-join` (10 a minute per account); an unknown code, a closed room and a removed account get one refusal on `/oyun`.
- **A newcomer.** `auth` sends a visitor to `/login` with the address kept as the intended one; from there the registration form (`auth/register`: Google first where it is configured, then name, e-mail, password twice, «Məni xatırla», the privacy note's tick) or the Google completion page (`auth/google-register`); `role.chosen` sends the new account to `/role?role=player` for the player's sentence; `verified` to the notice and the mailbox; the mail's link back to the intended address; and then the join page and «Qoşul». On elifba.io Google sign-in is on (ADR 008) and vouches for the address. A mail link that opens in another browser — a mail app's own view, another browser than the one WhatsApp opened — has no session: the person logs in there, and the code is lost in it.
- **What holds.** ADR 020: every player is an account, and the owner chose that over a typed name (the advisor's recommendation then). ADR 019: `verified` on the player group. G2: a visitor reads nothing of a room. CLAUDE.md: no third-party request from a page, and a name never in a URL.

## Decision

### Sharing the link

1. **A share row beside the QR and the code** (`ShareRow`, in `components/rooms/room-code.tsx`), two 44px `outline` buttons side by side:
    - on the host's start screen, under `InviteCard`'s address line, centred, at most `max-w-xs` wide;
    - in `CodeDialog`, under the QR and above «Bağla», the dialog's width — so behind the round's code chip (`CodeChip`) for anyone in a round and behind a player's «Dostunu çağır»: a player may send the link as they may show the QR.
    - **Not on the big screen** (`rooms/screen`): it is a laptop or a television across a room, its controls are for a mouse or a remote, and the phone that would send the link is in someone's hand. The screen keeps the QR, the code and the address.
    - Not on the join page, the door or «Oyunlar»: a person shares a game from inside it.
    - At 375 × 667 the row adds 52px to the start screen's invitation; the choice's row must stay on the first screen with up to six players. If I2 measures that it does not, the start screen's QR is drawn at 136px instead of 160 (120px under the standing card stays).
2. **WhatsApp is a link the person taps.** The first button, «WhatsApp» (`MessageCircle`, `aria-label` «Oyunun linkini WhatsApp-da göndər»), is an `<a>` to `https://wa.me/?text=` with the whole message encoded (`encodeURIComponent`), `target="_blank"`, `rel="noopener noreferrer"`: WhatsApp opens with its chat picker, on a phone in the app, on a laptop through WhatsApp's own page. The message is `rooms.share.text` — «Gəl, birlikdə oynayaq! Oyuna qoşul: :url» — with `:url` the room's `join.url` and nothing else: no name of the sender, a player or the host, no game, no ULID. A name never goes into a URL, and `wa.me`'s query is one. **It is not a request of the page:** the page loads nothing from WhatsApp — no script, button widget, icon, font or image — and makes no `fetch`; the tap is a navigation the person makes, like any link (CLAUDE.md "No third-party requests" holds as written). `noreferrer` keeps the room page's own address, with the room's ULID, from WhatsApp. No WhatsApp logo and no brand green: the mark is a trademark, not an asset `content/credits.json` can hold under an allowed license; the button is the app's own `outline`, its icon lucide's.
3. **The second button: the system's sheet, else copying.** Where the browser has a share sheet and the device is touched (`navigator.share`, a secure context and `(pointer: coarse)`), «Paylaş» (`Share2`) opens it with `{ text }` — the same message as WhatsApp's — so Telegram, Messages, mail or the sheet's own copy are one tap away; a cancelled sheet says nothing. Elsewhere (a laptop, or a browser without a sheet) «Linki kopyala» (`Copy`) writes `join.url` alone with `navigator.clipboard.writeText`, and for 2 s the button reads «Link kopyalandı» with `Check` (`aria-live="polite"`). Where neither exists — a page over plain HTTP, as `composer dev:lan` serves it — the row is the WhatsApp button alone. The choice is a pure function (`shareWay()`, `resources/js/rooms/share.ts`, Vitest) of what the browser has, never stored.
4. **What leaves the device.** The message goes where the person sends it, under WhatsApp's (or the chosen app's) own rules: the sentence and the link with the room's code and tag. When a link is sent, WhatsApp may open it to build a preview: that request reaches our server without a session and gets what any visitor gets — the general page tags every page carries (the welcome's title, line and picture), nothing of the room (decision 11). The code in a chat's history stops working when the room closes (ADR 020 decision 7), and its tag keeps an old link from reaching another room that later draws the same six digits (decision 5). `/privacy` says all of this in one new paragraph, `privacy.rooms.share`, under «Böyüklərin oyunları» (decision 18).
5. **The link carries the room's tag.** `join.url` becomes `{APP_URL}/oyun/{code}?t={tag}`: `RoomJoinLink::tag($room)` is the first 6 characters of `hash_hmac('sha256', 'room-link:'.$room->id, APP_KEY)` in lowercase hex, derived each time and stored nowhere. It is not a credential — a code still admits and a tag grants nothing — it only says which room the link was made for. `GET /oyun/{code}` with a `t` that is not the tag of the open room the code opens now answers the one refusal, `rooms.errors.unknown` on `/oyun`, counted by `room-join` like any try; without `t` (a typed address, an `/otaq/{code}` redirect, a QR of before) it is as without a tag. The QR on the start screen, in the dialog and on the big screen shows the same `join.url`, so a photographed QR obeys the same rule. The camera (`scannedCode()`) still accepts the address with a query and visits `rooms.join` with the six digits, as it does today. Codes are still unique only among open rooms (ADR 020 decision 3): without the tag, a link opened weeks later in a chat would put a person straight into a stranger's room that drew the same code (decision 7).

### Joining on open

6. **Opened by hand.** `App\Support\RoomInvitation::openedByHand(Request)` is true only for a request that is all of:
    - exactly `GET` — a `HEAD` request, which Laravel routes to the same action, never;
    - not speculative: no `Sec-Purpose` (Chrome's prefetch and prerender, its address bar's prerender too), `Purpose` (older prefetch, Inertia's own), `X-Purpose` (Safari's preload) or `X-Moz` (Firefox's prefetch) header, whatever its value;
    - not an Inertia visit (`X-Inertia`) and not a JSON client (`expectsJson()`);
    - a top-level document navigation: `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document` (not an `<img>`, a `fetch`, an `<iframe>` or an `<object>`);
    - started by the person: `Sec-Fetch-Site: none` — the browser itself began it: another app (WhatsApp, Telegram, a mail app) handed it the link, the phone's camera read a QR, or it was typed or chosen in the address bar, and no web page can produce `none` — **or** `Sec-Fetch-User: ?1`, a navigation with a person's tap or click behind it (a link in WhatsApp Web, in a mail read in a browser).

    Everything else is not by hand and gets today's join page with «Qoşul»: a link preview's fetcher, a prefetch or a prerender (a prerendered page that is then shown is that join page), an `<img>`, a `fetch`, an iframe, a page's script that navigates without a tap, a redirect a cross-site page started without one, Inertia (the code field's «Davam et», the camera's visit), a JSON client, and a browser that sends no fetch metadata (Safari before 16.4, Chrome before 76, Firefox before 90). The rule reads only headers the browser sets itself (a page cannot set `Sec-*`); it is a pure function of the request with a dataset test of each case.

7. **What an open by hand does** — `RoomJoinController::show`, after `rooms.enabled`, `auth`, `role.chosen`, `verified`, `role:player` and `throttle:room-join` as today, so it is always a signed-in, confirmed player account:
    - an unknown code, a closed room, an account the host removed, or a `t` that is not the room's tag: the one refusal on `/oyun` (`rooms.errors.unknown`), as today;
    - **the host** of the room: to the room as they are — a link never changes whether the host plays; that is «Mən də oynayıram» (`SetHostPlays`) alone;
    - a present player: to the room, as today;
    - opened by hand, or with the invitation under way for this code (decision 8): **`JoinRoom`** — a new row, or the row of a player who left — and a redirect to the room. The tap that opened the link is the person's consent, and the room page shows at once where they are and offers «Oyundan çıx»;
    - a locked or a full room (`JoinRoom`'s `ValidationException` on `code`): the join page as after «Qoşul» today — the code, the name with «Dəyiş», the reason, «Qoşul» to try again — and nothing else of the room;
    - anything else: the join page, as today, and «Qoşul» is `JoinRoom` (`POST /oyun/{code}`, unchanged).

    Each of these counts once against `room-join`, as `GET /oyun/{code}` does today; no limiter changes. `JoinRoom` itself does not change.

8. **The invitation under way.** The path from a tapped link to a ready account crosses Inertia forms (login, registration, Settings → «Rollar») whose redirects are not navigations by hand. So the open by hand is kept: `App\Http\Middleware\RememberRoomInvitation` (alias `rooms.invitation`), on `GET /oyun/{code}` and placed before `auth` (I2 orders it with `prependToPriorityList`), writes the session's `rooms.invitation` — `{code, tag, until}` — when `RoomsArea::enabled()` and the request is opened by hand, for every requester: a visitor, an account without a role, an unconfirmed one, one without the player role, a ready one. It reads no room (a visitor learns nothing from it) and writes nothing else.
    - It lasts `elifba.rooms.invitation_minutes` (60): long enough to register and read the mail, short enough that a forgotten tab does not join a game an evening later. A newer open by hand replaces it; a logout ends it with the session.
    - `GET /oyun/{code}` **pulls** it when it names this code (and the request's `t`, if any, is its tag): a ready account then joins as if opened by hand — at the end of the login, of the registration at the door, of Google's completion page, of Settings → «Rollar», of `/role`, of the mail's link or of the notice page looking again (decision 14). It is used once: joined, refused or sent to the room, it is gone. A request that is speculative, `HEAD` or JSON never pulls it.
    - The intended address (`url.intended`) still does the routing as today; the invitation only says that the person opened this link by hand in this browser. It holds a code and a tag, nothing about a person, and is never read for anything but this.
9. **The name one joined under.** With «Dəyiş» skipped, the name shows where the joiner lands: a player's start screen keeps «Qoşuldunuz» and «:name kimi», and gains a 44px `ghost` «Dəyiş» (`rooms.join.change_name`) after it, into Settings → Profil — the player stays present; ‹ and «Oyuna qayıt» bring them back. In a round the joiner's own side of the strip names them (ADR 027), and the final's standing marks their row «siz». A newcomer typed or kept the name a minute before, under «Oyunda adınız belə görünəcək.» (decisions 12–13). No toast: on a phone it would lie over `RoomActionBar` or the round. The join page that the rest still gets keeps «Oyunda adınız belə görünəcək:» and «Dəyiş».

### The newcomer

10. **Every player stays an account** ([020](020-rooms-and-joining.md)): the owner's choice is not reopened. What changes is the way to one: the player role is taken in the same step as the account, `/role` is skipped, and the code is carried to the end in the session (decision 8). `verified` stays on the player group (decision 14).
11. **The door.** A visitor whose open was by hand is sent by `auth` — `redirectGuestsTo(fn ($request) => RoomsArea::door($request) ?? route('login'))` in `bootstrap/app.php`; `door()` names `rooms.invited` only for a `rooms.join` request whose session holds the invitation (decision 8) while the switch is on — with `/oyun/{code}?t=…` kept as the intended address. Every other visitor goes to `/login` as today: a preview's fetcher, a prefetch and a browser without fetch metadata get today's path whole.
    - **`GET /oyun/qeydiyyat`** (`rooms.invited`, `RoomInvitedController::create`, page `rooms/invited` in the auth card, `AuthLayout`) — middleware `rooms.enabled`, `guest`: the only room route outside the player group. It renders while the session holds an invitation and sends the visitor to `/login` otherwise; a signed-in account is sent to `/start` by `guest`, as `/register` sends it.
    - **It shows nothing of the room**: not the code, the game, the host, who has joined, or whether the code opens anything — it reads no room, and the page is one and the same for a real code and six made-up digits (G2: a visitor reads nothing). The page's tags are every page's general ones (decision 4).
    - **At 375 × 667**, top to bottom: the auth card's header (the logo and the language switch); «Sizi oyuna çağırırlar» (`h1`) and the line «Oyuna Elifba hesabı ilə qoşulursunuz — bir dəqiqəyə hazır olur. Hesabınız var? [Daxil olun].», whose link goes to `/login` (the intended address kept); **«Google ilə davam et»** first, where Google sign-in is on; «və ya e-poçt ilə»; the form (decision 12). The title, the line, «Daxil olun» and the Google button stand on the first screen; the form's button is one scroll down (about 150px), as the registration form's is today. No install banner, no navigation.
12. **The short form and the role in the same step.** `POST /oyun/qeydiyyat` (`rooms.invited.store`, middleware `rooms.enabled`, `guest`, `throttle:room-invited` — 30 a minute per IP, as no account exists yet: a room's 20 players registering at once behind one Wi-Fi address stay inside it) → `App\Actions\Fortify\CreateInvitedPlayer`:
    - **Fields:** «Ad» (`autoComplete="name"`) with the line «Oyunda adınız belə görünəcək.» under it; «E-poçt ünvanı»; «Şifrə» **once**, with `PasswordInput`'s eye — no repeat: the address is confirmed before the first game (decision 14), so a mistyped password is mended by «Şifrəni unutmusunuz?»; «Məni xatırla», on by default with «Ortaq kompüterdə bu işarəni götürün.» (ADR 017, as the registration form).
    - **Two ticks, never merged, never pre-ticked** (§7 "Agreements"): «[Məxfilik qeydini] oxumuşam.» (`terms`, as registration), and under it the player's sentence, word for word, «Otaqlarda öz adımla oynayıram; adım və nəticələrim olduğum otağın oyunçularına görünür.» (`agreement`, `roles.agreement.player`). Each has its own error (`auth.register.terms_required`, `roles.errors.agreement`).
    - **«Hesab yarat və qoşul»** (`h-11`, full width, `Spinner` while it posts).
    - The action validates the name and the address as `CreateNewUser` does (`ProfileValidationRules`), the password with `Password::default()` and no `confirmed`, `terms` accepted and `RoleChoiceData::rules()`'s `agreement` accepted; in one transaction it creates the account as `CreateNewUser` does (`terms_accepted_at`, `locale`) and **gives the player role through `GrantRole`** with `new RoleChoiceData(Role::Player)` — which stamps `player_agreed_at` and sets `area`; `GrantRole` stays the only place a role is given. The controller then fires `Registered` (the confirmation mail), logs the account in with «Məni xatırla» as ticked (ADR 017), and redirects to the intended address. `/register`, its form and `CreateNewUser` do not change.
13. **Google first.** The door's Google button is the existing `GET /auth/google/redirect?remember=1|0`; the session keeps the invitation across the round trip.
    - An existing account linked or found by Google (ADR 008's rules) is logged in and goes to the intended address: in at once with the player role; through Settings → «Rollar» with «Oyunçu» preselected without it (ADR 019 decision 6), and in from there by the invitation.
    - A new one gets the completion page (`auth/google-register`), which **while the session holds an invitation and the switch is on** (prop `player: true`) adds the player's sentence as a second tick under the privacy note's, and says «Hesab yarat və qoşul»; `CreateUserFromGoogle` takes `$invited` from the controller, then requires `agreement` too and gives the role through `GrantRole` inside its transaction. The address is confirmed by Google, so the redirect to the intended address joins at once. Without an invitation the page is as today and the role is chosen on `/role`.
    - The ticks are not moved to the door before Google: the completion page is where the person first sees the name Google gives, and may shorten it, before any room shows it.
14. **The address is still confirmed.** `verified` stays on the player group (ADR 019): a name in a room is an account with a mailbox behind it, a removed stranger needs a new address to come back, and a mistyped address cannot hold a name. Google skips the mailbox. For the e-mail path the step is made gentler, not removed:
    - The notice (`auth/verify-email`) gets the prop `game` — true while the session holds an invitation and the switch is on — and then says one line more, «Məktubdakı keçidə toxunun: ünvan təsdiqlənən kimi oyuna keçəcəksiniz.».
    - **It looks again when it is shown again**, for every account: on `visibilitychange` to visible it reloads itself (`router.reload()`), so Fortify's prompt sends a confirmed account on to the intended address. A person whose mail's link opened in another browser confirms there, comes back to this tab, and is taken into the game by the invitation; the mail's link in the same browser joins directly.
    - The confirmation mail, Fortify's verification and the routes do not change.
15. **The alternative left to the owner: an unconfirmed account joins by an invitation.** The owner may choose instead that an account made at the door plays at once, before its address is confirmed. It would be built as a middleware in place of `verified` on the room routes that lets an unconfirmed account through for the one room its session's invitation joined it to (the room page, the state, answers, taunts, leaving, the voice), while «Oyunlar», opening a room and every other code keep `verified`, and the account must confirm before its next game. **Its gain:** the e-mail path is 4 taps and one page with no mailbox (decision 16). **Its risks:** an address typed wrong or someone else's holds a name in a room, and its owner may get a confirmation mail for an account they never made; a removed stranger comes back in a minute with an invented address, where today it costs a mailbox; names nobody vouched for are shown to a room; a password cannot be recovered until the address is confirmed; the player group gets the only exception to `verified` in the app (`RoleAreasTest` and ADR 019 would say so), and `/privacy` would say that an unconfirmed address is stored. **It is reversible both ways:** it changes a middleware and a paragraph, not a table. It is not what I2 builds.

### The switch

17. **With `elifba.rooms.enabled` off none of it exists:** `GET /oyun/{code}` and the door answer 404 (`rooms.enabled` first; `rooms.invitation` writes nothing while it is off); `RoomsArea::door()` is null, so a visitor goes to `/login`; the Google completion page offers no player's tick and the notice no line about a game (their props are false); there is no room page, so no share row; `/privacy`'s section, with `privacy.rooms.share`, is drawn only while it is on. `RoomsSwitchTest` checks each.

### What does not change

19. Every rule of ADRs 019–032 holds but the lines amended above:
    - **020** — a code admits a signed-in, confirmed account with the player role into one room and nothing else; one refusal; `locked`, `full`; the limiters; the routes' table; `JoinRoom`; `/oyun` and its field, the camera's own visit and «Davam et» still lead to the join page and «Qoşul» — a typed code may be mistyped, and the join page shows it to check before joining a stranger's room.
    - **021, 022** — the state and its version, the protocol, the channel's `room.changed`, `RoomWaits`, the points and the ranking: joining by a link is `JoinRoom`, as «Qoşul» was.
    - **024** — no name in a URL, a log or a broadcast; no age, nickname, chat or free text; nothing kept about a person across rooms; the message holds no name.
    - **026, 032** — the start screen's parts, «Dostunu çağır», the code chip, the frame; the share row is a part of the invitation they already hold.
    - **017** — «Məni xatırla» on the door as on the registration form; **008** — Google's address rules, linking and refusals.

## Consequences

- The person who is already a player is in the game with the tap that opened the link; a newcomer's path is a page and two ticks shorter, and with Google it never meets the mailbox.
- **A link is consent.** Anyone who can make a player tap a link to `/oyun/{code}` puts that player, with their name, in that room; today «Qoşul» stood between. A gesture is still needed (decision 6), the room page says at once where the player is, «Oyundan çıx» is one tap, and the host's lobby and «Çıxar» are unchanged (ADR 020 decision 8). The tag (decision 5) keeps an old link from reaching another room.
- Registration has two shapes: `/register` (the repeated password, the role chosen on `/role`) and the door (one password, the player role in the same step). An account made at the door can add another role in Settings → «Rollar» as anyone can.
- The notice page reloads itself when it is shown again, for teachers and parents too: a confirmed account is sent on without a manual reload.
- A browser without fetch metadata, and a link preview, get exactly today's path — the safe side of decision 6. I2 measures which browsers that is on the phones people use (To build, "Seen on devices") and records it in "As built"; a gap in a common browser amends this record before the rule is relaxed.
- One more route outside the player group, and a session key: `RoleAreasTest`, `RoomsSwitchTest` and `TeacherIsolationTest` name them.

## Alternatives rejected

- **Sharing.** WhatsApp's logo or green (a trademark; no asset under an allowed license); a WhatsApp script or button widget (a third-party request); the `whatsapp://send` scheme (fails without the app and on a laptop, where `wa.me` falls back to WhatsApp's page); a share button on the big screen (decision 1); Elifba sending invitations itself, by SMS or e-mail (it would store contacts, ADR 024); a short-link service (a third party, and a second address); the host's name or the game in the message (a name never in a URL; the game may change before the friend arrives); «Paylaş» on a laptop (its share menus differ; copying is what a mouse expects).
- **Joining on open.** Joining on any `GET` (a preview, a prefetch, a `HEAD`, an `<img>` or another site's script would put a signed-in player in a room); a script on the join page pressing «Qoşul» by itself (the same, with a flash of the page); a signed token per invitation (a second credential beside the code, against ADR 020 decision 3); joining from the code field or the camera without «Qoşul» (decision 19); a toast with the name (decision 9).
- **The tag.** No tag (an old link from a chat could join a stranger's room that drew the same code); never reusing a code (a table of retired codes to keep and prune, and a code space that fills).
- **The newcomer.** A player without an account (ADR 020; the owner's choice); `verified` relaxed (decision 15, left to the owner); the player's sentence merged into the privacy note, or ticked in advance (§7 "Agreements": two consents, each an act); the role given by the invitation without its sentence (no stamped agreement); the ticks on the door before Google, skipping the completion page (decision 13); a passwordless e-mail link (a new credential, against ADR 017's rules); a six-digit code typed from the mail instead of its link (a second confirmation mechanism for every account; revisit if E′ is common); `/register` with a mode for rooms (room text on every teacher's registration); `/login` as the visitor's first page (a newcomer would need one more tap to reach the form, and the login page speaks to teachers).

## What would make us revisit

- I2's device check finds a common browser that opens WhatsApp's links without `Sec-Fetch-Site: none` or `Sec-Fetch-User: ?1` (decision 6), or a link preview or prefetch that passes the rule.
- Players say they were put in a game by a link they did not mean to open.
- Newcomers are lost at the mailbox (the owner may then take decision 15, or a typed code from the mail).
- WhatsApp changes `wa.me`, or the door draws spam accounts past its limiter.

## As built (I2, 2026-11-19)

Built as decided; what the build names, adds or had to settle:

1. **`App\Support\RoomInvitation`** holds decision 6's rule and decision 8's session key: `openedByHand()`, `remember()`, `pending()`, `pull()`, `tagOf()` (the request's `t`: null without one, an empty string — a tag no room has — for a value that is not text, `?t[]=`) and `wellFormed()` (six lowercase hex characters); the key is `RoomInvitation::KEY`, `rooms.invitation`. `pending()` reads none while the switch is off (decision 17), so an invitation left in a session from before is never used, the completion page's `player` and the notice's `game` are false, and `RoomsArea::door()` is null.
2. **A malformed tag is not remembered.** `RememberRoomInvitation` keeps an open only without `t` or with a well-formed one: no room has any other, and `show()` refuses it as decision 5 says.
3. **The door is named for this link only.** `RoomsArea::door()` names `rooms.invited` when the pending invitation names the request's own code — a visitor whose session still holds another link's invitation goes to the login, as any other.
4. **`show()` takes the invitation first**, before the room is resolved, so that it is used once whatever the answer (decision 8: joined, refused or sent to the room). A host goes to the room for every request, as decision 7's table says — before I2 a host who had stepped out met the join page.
5. **Locked or full on open** answers in the same response: page `rooms/join` with the reason as the page's `errors.code`, never a redirect — a browser would follow a redirect as another open by hand. `rooms/join` shows `errors.code ?? arrived.code` on its «Qoşul» form.
6. **The door's form** lowercases the address as registration does (`fortify.lowercase_usernames`); the controller fires `Registered`, logs in with the box (`fortify.guard`), regenerates the session and goes to `redirect()->intended(GoogleSignIn::home())`. `CreateInvitedPlayer` validates first and then creates the account and calls `GrantRole` in one transaction; `CreateUserFromGoogle($profile, $input, $invited)` saves and grants in one transaction too, its refusal of a taken address unchanged. The limiter is `room-invited`, keyed `room-invited|{ip}`.
7. **The link's root.** `RoomJoinLink` builds `url` and `entry_url` on `APP_URL` without a port its scheme implies: docker-compose builds `https://elifba.io:443`, and a message read in a chat should say `https://elifba.io/oyun/…`, as a browser writes it; any other port (`composer dev:lan`'s `:8000`) stays. The QR, the copied link and the screen's poster carry the same address.
8. **The share row** (`ShareRow`, `components/rooms/room-code.tsx`) is a grid of two equal columns, one when `shareWay()` gives none; `InviteCard` draws it `mt-2 max-w-xs` under the address line, `CodeDialog` the dialog's width between the QR and «Bağla». The way is read with `useSyncExternalStore` (`shareAbilities()` in `rooms/share.ts`; none before the page runs). Measured at 375 × 667 with six present players: the share row stands at 354–398px, the choice's row ends at 474px and «Başla» begins at 603px, so the start screen's QR stays 160px (decision 1's 136px is not needed).
